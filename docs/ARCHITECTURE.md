# Архитектура и инженерные решения

## Почему Java Compiler API

Полный парсер языка уже входит в JDK. `JavacTask.parse()` создаёт AST без генерации байткода и без выполнения кода. Аннотационные процессоры отключены `-proc:none`. `SourcePositions` задаёт границы исходных фрагментов в UTF-16, совпадающие с индексами строк JavaScript. Emoji перед узлом не сдвигает правку: это проверяет интеграционный тест.

Парсинг отделён от type checking. Синтаксически корректный файл с неизвестным именем переменной можно визуализировать; quality gate отклонит его на стадии javac. Это не маскируется зелёным статусом анализа.

## Контракт представлений

Истина - текст Java. Граф является проекцией AST конкретной версии. Узел содержит тип, исходный span, отдельный редактируемый span, строку и фрагмент. Для `if` редактируется условие, а не весь блок. Для обычной инструкции редактируется инструкция целиком. После каждой операции текст снова парсится; синтаксически неправильная правка узла не принимается.

Нетронутый исходник не регенерируется pretty-printer: это сохраняет комментарии, отступы, литералы, классы и неподдерживаемые визуальные конструкции. Обратный переход выполняется splice-операцией по диапазону. При загрузке и экспорте кодировка UTF-8; консольная JVM также использует UTF-8.

GraphBuilder строит последовательность снизу вверх. `if` получает true/false связи, циклы получают обратную связь и выход. Для for явно представлены инициализация и update. Break/continue направляются к ближайшему структурному контексту. Switch statement учитывает fallthrough и default. Для try/catch связи исключений являются консервативными. Return через finally, labeled flow и switch expressions не выдаются за точный CFG: их семантика сохраняется в Java, а отображение частично структурное.

## Диагностика

Каждая рекомендация включает rule id, severity, methodId, строку и span. Применимость автозамены вычисляется отдельным AST-предикатом. Big O не выводится как доказанный факт: вложенность d циклов даёт условное `O(n^d)` только при линейном числе итераций каждого и постоянной стоимости тела. Сложность вызовов не учтена; рекурсия даёт «неизвестно». Предупреждение о `+=` выдаётся для явно объявленного String с учётом локальных блоков; числовые счётчики не помечаются.

## Проверяемая оптимизация

Распознаётся только точная форма:

```java
static int countPairs(int[] values) {
    int matches = 0;
    for (int a : values) {
        for (int b : values) {
            if (a == b) { matches++; }
        }
    }
    return matches;
}
```

Пусть значение v встречается f(v) раз. В упорядоченных парах, включая самопары, оно даёт f(v)² совпадений. Поэтому результат равен сумме квадратов частот. В новой версии счётчик и умножение остаются `int`: переполнение следует модульной арифметике Java, как и повторный increment. Коллизии HashMap учитываются реализацией карты; средняя сложность O(n), память O(k). Новая версия не сохраняет профиль выделения памяти и не гарантирует одинаковое поведение при OutOfMemoryError.

Любой дополнительный вызов, изменение массива, иное условие, дополнительная инструкция, другое возвращаемое значение или тип отклоняет шаблон. Строковые `.equals`, пользовательские `.id()` и `merge()` автоматически не переписываются: у них могут быть побочные эффекты, null-семантика и зависимость от порядка. Для них выдаётся рекомендация, а не рискованная замена.

## Декомпозиция

Переносится независимый static-метод без аннотаций, native, synchronized и прямой рекурсии. В исходном классе сохраняются сигнатура и доступность; тело делегирует `BlueprintFunctions`. Новый класс содержит прежнюю реализацию и imports. До принятия компилируется весь проект: скрытые зависимости от полей/методов и приватных типов отклоняют перенос. Это проверка зависимостей, не доказательство эквивалентности: меняется стек вызовов, поэтому исключения и трассировки могут отличаться и точное сравнение stderr это обнаружит на соответствующих входах.

## Quality gate

Обе версии собираются независимо в разные временные каталоги. Для каждого входа запускаются новые JVM. Стандартный ввод закрывается после передачи данных. stdout/stderr читаются параллельно, чтобы избежать блокировки заполненного pipe. При переполнении вывода или таймауте процесс и потомки завершаются. Значения вывода не trim-ятся и не нормализуются. Время выполнения не входит в критерий эквивалентности.

PASS: обе сборки успешны, задан хотя бы один вход, каждый запуск завершился в пределах ограничений, для всех входов совпали stdout, stderr и exitCode. Совпадение двух исключений с идентичным stderr и exitCode считается сохранённым наблюдаемым поведением. Даже одинаковые таймауты/обрезанный вывод не дают PASS.

## Модель развёртывания

1. Trusted local: loopback сервер; исполняются собственные проверяемые исходники. Ограничение памяти/времени процесса не ограничивает файловую систему или сеть ОС.
2. Host + Docker runner: отдельный read-only контейнер без сети и capabilities для каждого запуска, с лимитами CPU, памяти и процессов. Компиляция остаётся на хосте с отключёнными processors. Для публичной многопользовательской системы также нужна изоляция компиляции и отдельный worker/service boundary.
3. Compose: приложение целиком в ограниченном контейнере для воспроизводимости демо, без межпользовательской изоляции.
4. Sites: статический обзор реальных сохранённых данных; JVM там отсутствует. Нельзя выдавать записанный результат за выполнение загруженного кода.

Docker-путь не запускался в текущей среде. Перед публичным сервисом обязательны отдельная worker-нода/VM, аутентификация, квоты и нагрузочная проверка. Это следующая стадия, не реализованная гарантия текущего localhost-прототипа.
